## §6 MAX

Боевая конфигурация, прочитанная через `GET /api/max/admin`:

```
MAX_BOT_TOKEN_set:       true
бот отвечает:            да
webhook_url:             https://cmpas.ru/api/max/webhook
подписок зарегистрировано: 1
  подписка 1: url=https://cmpas.ru/api/max/webhook
MAX_WEBHOOK_SECRET_set:  false
```

**Про `false`.** Это не дефект кода и не забытая настройка: секрет заводит
сама выкладка. `scripts/deploy-production-remote.sh` при отсутствии
`MAX_WEBHOOK_SECRET` генерирует его (`openssl rand -hex 32`) и тут же
перерегистрирует подписку MAX с этим секретом. Выпуск не выложен, поэтому
на проде секрета ещё нет. Проверить «защита включена» на проде до выкладки
физически нечем — поведение проверено на стенде, ниже.

**Про коды ответа.** Приёмник отвечает `200 {"ok":true}` и принятому
обновлению, и отвергнутому — намеренно
(`src/app/api/max/webhook/route.ts:99`): иначе по реакции подбирают
секрет, а MAX на 200 не шлёт повторов. Поэтому код ответа приёмкой быть не
может. На проде проверено единственное, что здесь проверяемо:

```
POST без заголовка       -> 200 {"ok":true}
POST с неверным секретом -> 200 {"ok":true}
OK: ответы неразличимы — подобрать секрет по реакции нельзя
```

**Приёмка по следствию — на стенде** (`scripts/task28-max-webhook-stand.cjs`,
секрет и токен бота у стенда свои, поддельные, наружу не ходят):

```
1. без секретного заголовка   -> 200, привязки нет
2. с неверным секретом        -> 200, привязки нет
   оба отказа отвечают одинаково
3. с верным секретом          -> 200, клиент привязан (maxChatId проставлен)

ИТОГ: PASS
```

То есть fail-closed работает: без верного секрета обновление отбрасывается,
с верным — доходит до дела.
