# ТЗ для Codex: подготовка КОМПАС к бета-тесту на психологах

> Контекст: `docs/strategy.md` (Горизонт 1), CJM-схемы: `docs/cjm-beta.md`.
> Психолог — в Android-приложении/вебе; клиент — в MAX/Telegram, fallback — web-ссылки.
> Правила: дизайн-палитру не менять; Prisma-изменения — только через миграции;
> не ломать существующее; каждая кнопка должна делать реальное действие (`// TODO API`
> допустим только там, где бэкенда объективно нет).

Приоритеты: **P0 = блокер беты**, P1 = до конца беты, P2 = после.

## EPIC A (P0) · Привязка клиента к мессенджеру «на раз-два»

### A1. Android: чинить InviteSheet — шарить настоящую ссылку
**Сейчас:** `android/.../presentation/comms/CommunicationSheets.kt:128` (`InviteSheet`)
показывает и отправляет в share-sheet **сфабрикованную** строку
`cmpas.ru/i/${clientId.take(8)}-tg|mx`, которая никуда не ведёт. При этом
`ClientDetailViewModel.kt:118` уже вызывает реальный `POST /api/mobile/clients/{id}/invite`
(`CompasApi.kt:76`) и кладёт настоящий `inviteLink` в `uiState.inviteLink` — но UI его
не использует.

**Сделать:**
1. `InviteSheet` при открытии дожидается ответа `createInviteLink` (лоадер-скелетон),
   отображает и шарит **только** реальные ссылки из ответа API:
   `inviteLink` (smart `/connect/<token>`) — основная; `directLinks.telegram` /
   `directLinks.max` — для кнопок каналов.
2. Убрать генерацию фейковой строки полностью.
3. Кнопка «Поделиться» → системный share-sheet с `shareText` из ответа API
   (там уже готовый текст приглашения).
4. Обработать ошибку сети: состояние «Не удалось создать приглашение — повторить».

**Критерии приёмки:** созданная в приложении ссылка открывается на чужом телефоне,
ведёт на `/connect/<token>`, после тапа по кнопке канала клиент попадает в бот и
привязывается; в БД `ClientInviteToken.usedAt` заполняется.

### A2. Android: QR-код в InviteSheet
**Зачем:** самый частый сценарий — клиент сидит напротив психолога в кабинете.

**Сделать:**
1. В `InviteSheet` над кнопками — QR-код умной ссылки `inviteLink`
   (генерация локально; ZXing-core как зависимость или отрисовка BitMatrix в Compose
   Canvas — без Google Play Services).
2. Подпись: «Покажите экран клиенту — пусть наведёт камеру».
3. QR и ссылка — один и тот же токен, ничего дополнительно не создавать.

**Критерии:** сканирование камерой iPhone/Android открывает `/connect/<token>`.

### A3. Android: живой статус привязки
**Сейчас:** после отправки приглашения `SentState(delivered=false)` всегда, психолог не
узнаёт о результате без ручного refresh.

**Сделать:**
1. Пока `InviteSheet` открыт — поллинг `GET /api/mobile/clients/{id}/channels`
   (`route.ts` уже существует) каждые 3–5 сек.
2. При появлении канала: экран успеха «✓ {Имя} подключён(а) к {MAX|Telegram}» +
   haptic; карточка клиента обновляет `hasMessenger`/чип канала без перезахода.
3. После закрытия шита поллинг останавливается (lifecycle-aware).

**Критерии:** привязка клиента на втором устройстве отражается в открытом шите ≤5 сек.

### A4. Сервер: единый токен-лукап в Telegram-боте
**Сейчас:** `src/lib/channel-binding.ts:65` хранит **sha256-хэш** токена, а
`src/lib/telegram-bot.ts:112` (обработчик `/start c_<token>`) ищет по **raw**-значению —
этот путь мёртв; спасает только перехват в `src/app/api/telegram/webhook/route.ts:15`.

**Сделать:** в `telegram-bot.ts` заменить прямой поиск на канонический
`consumeClientChannelInvite()` из `channel-binding.ts` (или удалить дублирующую ветку,
оставив перехват в webhook как единственный путь). Один источник истины.

**Критерии:** привязка работает и когда update доходит до `bot.start` (например, при
локальном long-polling), unit-тест на оба пути.

### A5. Web `/connect/<token>`: MAX первым
**Сейчас:** `src/app/connect/[token]/ConnectClient.tsx` — Telegram первый; MAX без
`MAX_BOT_USERNAME` показывает «временно недоступно».

**Сделать:**
1. Порядок кнопок: **MAX → Telegram** (реальность РФ: Telegram требует VPN).
2. Подписи честные: Telegram — «может требовать VPN в РФ»; MAX — «работает без VPN».
3. Автовыбор в мобильном авто-редиректе (350ms) — MAX, если ссылка доступна.

## EPIC C (P0) · Расписание с телефона

### C1. Блокировки времени — на сервер, а не в SharedPreferences
**Сейчас:** `android/.../data/local/LocalScheduleBlockStore.kt` хранит блокировки
локально как фейковые Session (`clientId="local-block"`); `POST /api/mobile/blocks`
существует (`src/app/api/mobile/blocks/route.ts`), но **не вызывается никем**
(`api.createBlock` — 0 использований). Клиентская самозапись эти блокировки не видит.

**Сделать:**
1. `QuickActionViewModel.kt:156` (`"block-time"`): вместо `blockStore.saveBlock` →
   `api.createBlock`; при офлайне — сохранить локально с флагом `pendingSync` и
   досинхронизировать при следующем старте (WorkManager не обязателен — досылка при
   запуске достаточна для беты).
2. `CalendarViewModel.kt:55`: блокировки читать из `GET /api/mobile/blocks`
   (локальный стор — только как кэш).
3. Удаление блокировки из календаря → `DELETE /api/mobile/blocks/{id}`.
4. Миграция: при первом запуске новой версии залить существующие локальные блокировки
   на сервер и пометить синхронизированными.

**Критерии:** блокировка, созданная в приложении, исчезает из свободных слотов
самозаписи (`/bot/book/...`) немедленно; видна в веб-календаре.

### C2. Экран «Расписание» в Android (мобильный минимум)
**Сейчас:** в Android нет ни одного экрана про доступность (grep по
availability/scheduleRule — 0 совпадений). Полный редактор есть только в вебе
(`src/app/diary/availability/page.tsx`).

**Сделать (не копировать веб-редактор!):**
1. Новый пункт в Профиле: «Расписание» → экран:
   - переключатель режима записи: Закрыта / Превью / Открыта
     (`scheduleMode` из настроек);
   - неделя read-only: правила и слоты (цвет/время/формат);
   - быстрые действия: «Заблокировать время», «Выходной/отпуск на даты»
     (используют C1);
   - ссылка «Тонкая настройка правил — в веб-кабинете» (открывает
     `https://cmpas.ru/diary/availability`).
2. Новые mobile-endpoints (тонкие обёртки над существующими server actions
   `src/app/diary/actions/availability.ts`, `schedule-rules.ts`, `settings.ts`):
   - `GET /api/mobile/availability` → слоты + правила + scheduleMode;
   - `PATCH /api/mobile/availability/mode` → смена scheduleMode.
   Auth — как в остальных `/api/mobile/*`.

**Критерии:** с телефона можно закрыть запись, взять выходной и заблокировать вечер —
и всё это мгновенно отражается в самозаписи клиентов.

### D2. Android: центр уведомлений вместо AlertDialog

### D3. FCM-push
**Сейчас:** всё заглушено: `google-services` закомментирован
(`android/app/build.gradle.kts:8`), `google-services.json` нет, токен не запрашивается,

**Сделать:**

2. `FirebaseMessagingService`-наследник: `onNewToken` → `POST /api/mobile/fcm`;

4. Тихие часы 21:00–9:00 по таймзоне психолога (пока константа, настройка — потом).

**Критерии:** самозапись клиента приводит к пушу на телефоне психолога ≤30 сек;

## Порядок работ и зависимости

```
A4 (фикс токенов) ──┐
B1 (env MAX)      ──┼─→ A1 → A2 → A3 (инвайт-флоу в Android) → B2, B3

```

## Definition of Done беты
- [ ] Психолог привязывает клиента к MAX за ≤2 действия клиента (QR или ссылка), видит
      «✓ подключён» без ручного refresh.
- [ ] Telegram-путь работает у клиентов с VPN; честные подписи о доступности.
- [ ] Блокировка времени с телефона мгновенно закрывает слоты самозаписи.
- [ ] С телефона можно закрыть/открыть запись и взять выходной.
- [ ] Push о подтверждении/отмене/самозаписи приходит на телефон; колокольчик ведёт в
      центр уведомлений с историей и read-state.
- [ ] Статусы напоминаний в приложении совпадают с фактом отправки сервером.
- [ ] `gradle assembleDebug` зелёный; CI зелёный; ни одна существующая фича не сломана.
