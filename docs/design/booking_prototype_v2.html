Экран 0 · Ссылка и «Поделиться»

Человеческий адрес вместо cuid

Специалист выбирает адрес при первом входе; старый адрес продолжает работать вечно и ведёт на новый. Кнопка «Поделиться» одинаковая во всех четырёх местах, где её могут искать: главный экран, расписание (включая мобильную ширину), карточка клиента, приложение.

Сейчас в проде: адрес — сырой cuid психолога (cmpas.ru/bot/book/<id>) везде, включая уже готовый компонент «Поделиться». Слот под слаг в БД не заведён.
psychologistSettings — нет поля slug
src/lib/share/buildShareUrls.ts — строит URL из сырого id, слаг не участвует
src/app/diary/availability/page.tsx:97 — bookingUrl хардкодит /bot/book/${'{'}id{'}'}
Экран 1 · Подбор времени

Не сетка на месяц, а три времени

Уже реализовано и работает правильно: чипы предпочтения, три подобранных времени, лист ожидания на пустом состоянии. Единственное, чего не хватает — часового пояса клиента при показе времени.

Статус: механика в коде верна. Это единственный экран прототипа, который можно взять как образец правильной реализации для остальных.
src/lib/booking/suggested-times.ts — готово, не трогать
src/app/bot/book/[psychologistId]/page.tsx — время без явного часового пояса, добавить подпись
Экран 2 · Возврат по ссылке (S1-R)

Спокойное узнавание вместо чистого листа

Человек ушёл подумать — это норма, а не отвал воронки. Запоминаем только предпочтение и дату визита на 30 дней, ничего личного. Ни слова «вы не завершили», специалист не видит, что кто-то заходил.

Сейчас в проде: экран отсутствует полностью. Возврат по ссылке показывает чистый первый экран, как будто визита не было.
не существует — ни компонента, ни хранения preference/last_seen (localStorage или link_session), нигде в src/app/bot/book
Экран 3 · Бронь

Два поля, без анкеты о себе

Реализовано верно: имя, телефон, согласие по-настоящему (не мелким шрифтом), ничего о запросе и состоянии не спрашивается.

Статус: в целом готово. Проверить только текст правила отмены — сейчас формулировка ссылается на удержание, которого больше нет.
Экран 4 · Подтверждение

Канал называется настоящим именем

Экран после записи должен называть канал, из которого человек на самом деле пришёл — Max, Telegram, что угодно ещё. Переключатель слева наглядно показывает разницу с текущим поведением.

Сейчас в проде: текст захардкожен на «Уведомление придёт в Telegram» для всех, включая пришедших из Max.
src/app/bot/book/[psychologistId]/page.tsx:464 — «Уведомление придёт в Telegram» без условия
src/app/bot/book/[psychologistId]/page.tsx:768 — тот же текст повторно, тоже безусловно
Экран 5 · Перенос без денег

Перенос — это перенос, а не вторая бронь

Старое время снимается ровно в момент подтверждения нового. Курьерская вежливость к листу ожидания — без денег, без гонки, одним сообщением.

Статус: сам перенос уже атомарный и написан хорошо. Уведомление листа ожидания при отмене/переносе — отдельная, отсутствующая часть.
src/lib/session-reschedule.ts — rescheduleSessionAtomic, готово, не трогать
src/app/client/reschedule/[sessionId]/ — клиентский перенос по подписанной ссылке, готово, не трогать
уведомление листа ожидания при освобождении часа — не существует
Экран 6 · Итог переноса

Тихий лист ожидания

«Тихий» в буквальном смысле: ни счётчиков «осталось мест», ни давления кто-то другому. Одно сообщение тому, кто ждал именно это время.

Сейчас в проде: лист ожидания принимает заявки (submitWaitlistInterest), но ничего не делает с ними при освобождении часа.
Экран 7 · «Мои встречи»

Постоянная дверь, а не тупик

Работает по подписанной ссылке в любом браузере и на любом устройстве — не только внутри Telegram. Показывает будущие встречи и, впервые, прошедшие.

Сейчас в проде: страница /bot/client узнаёт клиента только внутри Telegram WebApp или по localStorage на том же устройстве. Прошедших встреч не показывает вовсе.
src/app/bot/client/page.tsx — нет чтения токена из URL, только tg.initDataUnsafe и localStorage
src/lib/client-workflow.ts — personalClientToken уже есть и подписан, но эта страница им не пользуется
вкладка «Прошедшие» — не существует
Экран 8 · Специалисту вечером

Дальше всё зависит от факта, а не от расписания

Клиенту, который не пришёл, писать «спасибо за встречу» — оскорбительно. Отметка специалиста — развилка перед следующим экраном, и должна существовать до него, а не вычисляться из часов.

Сейчас в проде: такого списка нет. Единственная пост-сессионная механика — старый опрос самочувствия смайликами, выключенный по умолчанию.
src/lib/cron/post-session.ts — это опрос настроения (mood_1..5), не механика v2
одним тапом «Была / Не пришла / Перенесли» на сегодняшние сессии — не существует
нет статуса no_show в используемых значениях DiarySession.status
Экран 9 · Клиенту через 2 часа

Главный источник повторных встреч

Короткое сообщение с одной кнопкой на конкретное время — не опрос, не оценка. Отправляется только после отметки «была/был» с экрана 8.

По приоритету продукта: это заявлено v2 как «главный WOW» механики (§2.4) — и полностью отсутствует в текущей реализации.
Экран 10 · Через неделю

Одно сообщение и тишина

Право не продолжать — это право, а не проблема воронки. Ровно одно сообщение, если через неделю нет следующей брони; дальше — молчание.

Сейчас в проде: отсутствует. ScheduledClientMessage — общий механизм рассылки, годится как транспорт, но триггер «нет записи через 7 дней» нигде не создаёт для него запись.
Прототип показывает механику, порядок решений и текст сообщений — не финальную вёрстку. Цвета и радиусы — рабочие значения токенов из PRACTICE_handoff_booking.md §4, а не приблизительные: экраны в проде сейчас используют три разных оттенка зелёного (#1e3a2f на экране записи, #1a4d3a на экране переноса) вместо одного --accent:#2F5D50 — сверяйте пипеткой, а не на глаз.
