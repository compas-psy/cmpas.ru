> **Для исполнителя (Codex / Claude / любая модель).** Это ТЗ самодостаточно:
> для каждой задачи указаны файлы с текущим поведением, требуемое поведение и
> критерии приёмки. Прочитай «Глобальные правила» перед началом. Задачи внутри
> приоритета можно делать в любом порядке, если не указана зависимость.

## Персона и сценарий аудита

**Марина, 34** (персона из strategy.md §2.2): гештальт-терапевт, 5 лет практики,
18 клиентов, 70% онлайн. Установила КОМПАС, чтобы: перенести календарь, вести
запись, ставить/переносить/отменять сессии, писать заметки, готовиться к
сессиям по прошлым заметкам, напоминать клиентам, получать подтверждения,
дать клиентам самим отменять/переносить, подписывать оферту и отслеживать
согласия.

### Что Марина сказала после недели использования (сжатый фидбек)

1. **«Перенести весь календарь» — обман.** Импорт вытащил только повторяющиеся
   имена из заголовков событий. Ни одна из 40 будущих сессий не перенеслась —
   всё пришлось вбивать руками. Клиентку, которая ходит раз в месяц, импорт
   вообще не увидел.
2. **Заметка с телефона исчезает в вебе.** Написала «По блокам» на телефоне
   после сессии — в вебе это серый плоский текст. Написала структурную заметку
   в вебе — на телефоне её **вообще нет**. Перестала понимать, где источник
   правды, и завела параллельно заметки в Notion. Это провал ядра продукта.
3. **Голосовая заметка — фикция.** Нажала микрофон, поговорила, сохранила —
   осталась строка «ожидает расшифровки». Ничего не записалось. Чувство обмана.
4. **Приложение не знает, что сессия прошла.** В 15:50 сессия закончилась —
   карточка так и висит «подтверждена», в «следующей сессии» до вечера торчит
   уже прошедшая. Никто не предложил написать заметку. Чтобы сессия «прошла»,
   надо самой найти кнопку «Проведена ✓» в календаре веба.
5. **«Отметить оплату» — кнопка-пустышка.** Тост «Оплата отмечена» — и ничего.
   На карточке всё равно «Оплата: В порядке» у всех. Веду оплаты в блокноте.
6. **Согласие «подписано» открытием ссылки.** Клиент кликнул — и уже «дал
   согласие на обработку ПДн». Ни галочки, ни кнопки «Принимаю». Перед
   152-ФЗ-проверкой мне с этим некомфортно. И нет списка «кто ещё не подписал» —
   только заходить в каждую карточку.
7. **Клиент отменил за 4 минуты до начала — система позволила.** Ни отсечки,
   ни правила отмены (в онбординге я вводила «отмена за 24 часа» — оно нигде
   не работает).
8. **Онбординг спросил и забыл.** Ввела обеденный перерыв и перерыв между
   сессиями — в расписании их нет (поля не сохраняются). Шаг 3 из 7 вообще
   повторяет шаг 2. На Android онбординга нет совсем — пустой экран.
9. **Мелочи, которые выдают сырость:** «Требует внимания» называет незаполненные
   заметки «Домашние задания не заполнены»; переходы между разделами
   перезагружают страницу; кнопка переключения вида в дашборде не нажимается;
   рейтинг «—».

**Стратегический вывод:** сильная архитектура каналов и записи уже есть, но
«сарафанное радио» ломается о три вещи: (а) данные психолога не едины между
телефоном и вебом, (б) приложение пассивно — не проживает день вместе с
психологом (не знает, что сессия прошла), (в) кнопки-обманки подрывают доверие
быстрее, чем фичи его создают. Правило: **лучше честное «скоро», чем стаб.**

## Глобальные правила для исполнителя

1. **Дизайн не менять** без явного запроса: палитра `#1a4d3a`/`#c9a961`/`#faf8f5`,
   iOS-like, glass-компоненты Android (`GlassCard`, `CompasBottomSheet`,
   `PrimaryButton`/`GhostButton`), существующие компоненты веба.
2. **Prisma:** изменения схемы — только через `prisma/schema.prisma` + файл
   миграции в `prisma/migrations/<date>_<name>/migration.sql` + дублирование
   idempotent-DDL в `deploy/schema-fixes.sql` (так принято в проекте).
3. **Не ломать существующее.** Обратная совместимость API `/api/mobile/*`
   обязательна: старые APK в проде.
4. **CI перед мерджем:** `Channel Binding CI` (tsc + eslint web, gradle Android)
   и `Android Build` должны быть зелёными. Мердж в `main` = деплой в прод.
5. Все пользовательские тексты — по-русски, тон бережный (strategy.md §5.2:
   «Если будет удобно…», не «Вы должны…»).
6. Роутинг в вебе — через Next router (`useRouter().push`), не
   `window.location.href`.

### NOTES-1. Единые заметки телефон↔веб (source of truth = structuredNotes)
Ядро продукта (NSM «заметок/нед»), самая важная задача ТЗ.
- **Файлы:** `android/.../notes/PostSessionNoteScreen.kt` (buildText :69-83),
  `android/.../notes/PostSessionNoteViewModel.kt` (:36, :47),
  `src/app/api/mobile/sessions/[id]/route.ts` (GET и PATCH),
  `src/lib/smart-notes/config.ts` (SMART_BLOCK_DEFINITIONS),
  `prisma/schema.prisma` DiarySession (:348-351).
- **Сейчас:** Android пишет всё плоским текстом в `notes`; веб пишет структуру
  в `structuredNotes`+`privateNotes`+`clientSummary`. Телефонная заметка в вебе —
  серый legacy-блоб (и только если нет блоков); веб-заметка на телефоне не
  видна вовсе.
- **Надо:**
  1. PATCH `/api/mobile/sessions/[id]`: принять новое опциональное поле
     `structuredNotes` (массив блоков в том же формате, что пишет веб —
     см. `note-actions.ts:49-66`). Android режим «По блокам» отправляет блоки
     `Запрос/Наблюдение/Интервенция/Динамика/Следующий шаг` как структурные
     блоки с типами из SMART_BLOCK_DEFINITIONS (сопоставить ключи; если ключа
     нет — создать в конфиге). Режим «Кратко» — один текстовый блок. Поле
     `notes` продолжать заполнять сжатым plain-text (обратная совместимость
     со старыми APK и legacy-выводом).
  2. GET `/api/mobile/sessions/[id]`: возвращать `structuredNotes` как есть +
     собранный из него `notesPlain` (для старых экранов). Android
     `PostSessionNoteViewModel` при загрузке восстанавливает блоки из
     `structuredNotes`, а не из `notes` (:36).
  3. `previousNotesSummary` (`route.ts:30-46`): строить из `structuredNotes`
     (склейка заголовок: текст), fallback `clientSummary`, потом `notes`.
- **Приёмка:** заметка «По блокам» с телефона видна в вебе как структурные
  блоки в таймлайне клиента; структурная заметка из веба открывается на
  телефоне в режиме «По блокам» с заполненными полями; старый APK (шлёт только
  `notes`) не ломается; `npx tsc` и gradle-сборка зелёные.

### VOICE-1. Голосовые заметки: честное состояние вместо фикции

## P1 — ежедневный CJM

### COMPLETE-1. Жизненный цикл «сессия прошла» + нудж на заметку психологу
- **Файлы:** новый кусок в `src/lib/cron/*` (по образцу `post-session.ts`),

  `src/lib/notifications.ts` (createNotification), Android
  `DashboardScreen`/`attentionItems`.
- **Сейчас:** `completed` ставится только вручную кнопкой в веб-календаре
  (`calendar/page.tsx:752-758`); прошедшие сессии вечно висят «confirmed»;
  дашборд считает их «следующими»; список «сессии без заметок» ловит только
  уже-completed; нудж после сессии получает только КЛИЕНТ (mood-check).
- **Надо:**
  1. Cron (каждые 15–30 мин): сессии `confirmed` с
     `date+endTime < now - 15 мин` → `status='completed'` автоматически.
     `pending` прошедшие — НЕ трогать (психолог решит: no-show/отмена).
  2. При автозавершении, если у сессии нет заметок (`notes` И `structuredNotes`
     пусты) — `createNotification(type='session_needs_note',
     title='Сессия с {имя} завершена', subtitle='Самое время для заметки —
     если будет удобно')` психологу.
  3. Тип `session_needs_note` добавить в Android
     `NotificationCenterSheet.notificationIcon/Tint` (иконка EditNote) с
     переходом по тапу в PostSessionNote (sessionId уже есть в модели).
  4. Дашборды: «следующая сессия» не должна показывать прошедшие
     (уже частично решится автозавершением).
- **Приёмка:** через ≤30 мин после конца сессия сама становится «проведена»;
  психолог получает уведомление с переходом прямо в экран заметки; pending
  прошедшие не автозавершаются.
