# CLAUDE.md — Инструкции для агента

## Правила работы агента

- **После каждой задачи**: открыть pull request в ветке `feature/<id>`. Мёрж в `main` и деплой (GitHub Actions: деплой сервера + Android-билд) — исключительно решение учредителя, агент их не выполняет.

## Имена сборок и релизов (общее правило трёх продуктов)

```
Имя файла:         simpas-<продукт>-<версия>.apk
Тег релиза:        <продукт>-v<версия>
Постоянная ссылка: https://cmpas.ru/updates/latest/<продукт>.apk
```

`<продукт>` — ровно одно из: `praktika`, `zapiski`, `momenty`.
**Этот репозиторий выпускает `praktika`.** Пример: `simpas-praktika-1.0.6.apk`,
тег `praktika-v1.0.6`, ссылка `https://cmpas.ru/updates/latest/praktika.apk`.

Приставка `simpas` — по имени системы, объединяющей три продукта, а не по имени
одного из них: до этого правила КОМПАС транслитерировался одновременно тремя
способами — `kompas` в МОМЕНТАХ, `compas` в ПРАКТИКЕ, `cmpas` в домене.

- Без хеша коммита и без номера прогона: человек видит это имя в загрузках, и
  суффикс вида `-a3f9c21` ему ничего не сообщает. Версии достаточно.
- Релиз соответствует ВЕРСИИ, а не прогону сборки. Пересобрали ту же версию —
  обновите существующий релиз и его файл, новый не создавайте.
- `versionCode`/`versionName` не увеличиваются от правок сборки, подписи,
  разрешений или имён: это исправление доставки, а не новая версия продукта.

**Не переименовывать:** `applicationId` (`ru.cmpas.app`) — его смена означает,
что для системы это ДРУГОЕ приложение, обновление поверх установленного
перестанет работать и у людей окажутся две иконки. Ключ подписи — по той же
причине. Домен `cmpas.ru` и организацию `compas-psy` правило не касается.

Правило стережёт сборка, а не память: `scripts/check-release-naming.sh` зовётся
в CI на готовом артефакте и роняет сборку при расхождении
(`tests/release-naming.test.ts` проверяет самого сторожа).

## Стратегия проекта

**ВСЕГДА читай `docs/strategy.md` перед началом работы.**

КОМПАС — спокойная рабочая среда для помогающих специалистов (психологов, коучей, профориентаторов). Не CRM. Единое место для ведения всей практики.

## Принципы разработки

### UX (НЕ МЕНЯТЬ БЕЗ ЗАПРОСА)
- Палитра: `#1a4d3a` (зелёный), `#c9a961` (золото), `#faf8f5` (крем)
- iOS-style, минимальный интерфейс, без «админки»
- **Дизайн не трогать без явного запроса пользователя**

### Продуктовые принципы
- Никакого gamification (нет streak'ов, бейджей)
- Приватность по умолчанию (клиент не видит гипотезы специалиста)
- Опциональность: каждая фича включается специалистом
- Messenger-agnostic: ядро в вебе, мессенджер — слой
- Beachhead: растущий практик (3–7 лет, 12–25 клиентов)

### Технические принципы
- Next.js App Router, TypeScript, Tailwind CSS 4
- Prisma + PostgreSQL — при изменении схемы создавать миграции
- Server Actions для форм и данных
- Не ломать существующий функционал

4. Обновляй чек-лист выше по мере реализации
