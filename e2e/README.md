# Сквозные проверки выпуска (Задача 27)

Эти тесты идут против ЗАПУЩЕННОГО приложения с настоящей базой. Они не
входят в `npm test` и в обычный прогон CI не включаются: им нужен сервер,
PostgreSQL и засеянная практика.

Проверяется состояние экрана после действия, а не код ответа. Кнопка,
которая вызвала API и оставила экран прежним, — это работающий запрос, а не
работающий сценарий.

## Как запустить

```bash
# 1. Одноразовая база с полной цепочкой миграций
createdb praktika_e2e
DATABASE_URL=<praktika_e2e> npx prisma migrate deploy

# 2. Синтетическая практика: специалист, клиенты, расписание, встречи.
#    Настоящих людей в посеве нет — вымышленные имена и домен .invalid.
DATABASE_URL=<praktika_e2e> node scripts/e2e-seed.cjs

# 3. Приложение
npm run build
DATABASE_URL=<praktika_e2e> AUTH_SECRET=<любой> AUTH_TRUST_HOST=true \
  AUTH_URL=http://localhost:3100 npx next start -p 3100

# 4. Прогон
E2E_BASE_URL=http://localhost:3100 npx playwright test
```

Если браузер лежит не там, где его ищет Playwright, путь задаётся снаружи:

```bash
E2E_CHROMIUM=/opt/pw-browsers/chromium-1194/chrome-linux/chrome npx playwright test
```

## Важно: база одноразовая

Набор оставляет в базе следы — записанных клиентов, закрытые пункты
«требует внимания». Повторный прогон без пересева падает на собственном
следе. Это свойство набора, а не продукта: сценарии проверяют настоящие
мутации, а не их имитацию.

## Что внутри

| Файл | О чём |
|---|---|
| `release-paths.spec.ts` | критические сценарии выпуска: кабинет, внимание, заметка, запись клиента, конфликт часа, чужой доступ |
| `visual-web.spec.ts` | снимки 14 поверхностей кабинета на трёх ширинах + проверка на горизонтальное переполнение |
| `visual-public.spec.ts` | снимки клиентского экрана записи и проверка, что на нём нет технических терминов |

Снимки складываются в `artifacts/praktika-mvp/task27/`.
